== Example of an Accepted Client with DGGS obfuscation

=== General

This annex combines the Accepted Clients conformance class (<<clause-accepted-clients>>) with the DGGS conformance class (<<clause-dggs>>). An accepted client masks the position of the user on the device: it converts the position into a DGGS zone identifier and sends only a reference to that Cell. The implementation enforces this behaviour through the WriteProfile properties `locationPolicy` and `maxZoneLevel` (<<req_dggs_write-zone-level>>), so that the precise position is never transmitted and never stored.

The example uses the application _QuietWalk_ of the environmental office of the fictitious city of Musterstadt. Citizens carry their smartphone on walks and the application records the noise level every minute. A trail of precise positions every minute would reveal the home, the daily routine and the places a person visits. The application therefore reports each measurement only with the H3 zone at level 10 (about 15 000 m²) that contains the position.

The zone identifiers are those of <<tab-dggs-example-zones>>. All names, identifiers and URLs are fictitious.

----

The WriteProfile permits Things, Datastreams and Observations, but neither Locations nor FeaturesOfInterest. `locationPolicy` `cell-only` forbids any coordinates in a request and requires a Cell association for every Observation; `maxZoneLevel` 10 forbids references to finer Cells. `clientSideProcessing` declares the resulting resolution on the device: the edge length of an H3 zone at level 10 is about 76 m. `freeTextPolicy` `none` is verified against the schemas (<<req_accepted-clients_free-text-policy>>): names and descriptions are fixed values, so they are released without an Agreement. The FeatureOfInterest that the implementation derives from a Cell is generated by the implementation and is released without an Agreement as well (<<req_gdpr_release-free-text>>).

=== Masking on the device

The application determines the position with the positioning service of the smartphone and immediately converts it into the zone identifier at level 10. Only the zone identifier leaves the device:

[source,javascript]
----
import { latLngToCell } from "h3-js";

// precise position from the positioning service, kept only in memory
const { latitude, longitude } = position.coords;   // 41.385283, 2.173455
const zoneId = latLngToCell(latitude, longitude, 10); // "8a394460e407fff"

const observation = {
  phenomenonTime: new Date().toISOString(),
  result: laeq1min,
  Cell: { "@iot.id": zoneId }
};
----

The operator can rely on this behaviour without trusting the application: a release that sent coordinates or a finer zone would be rejected by the implementation (<<tab-acdggs-requests>>).

=== Writing observations

With an access token for `quietwalk-mobile` 1.4.0 (compare <<example-ac-token>>), the application creates a Thing without Locations and a Datastream. The Datastream is bound to WriteProfile 5 (<<req_accepted-clients_provenance-binding>>). It then posts one Observation per minute:

[[example-acdggs-observation]]
.Observation created by QuietWalk 1.4.0
[source,http]
----
POST /v1.1/Datastreams(77)/Observations
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...
Content-Type: application/json
----

[source,json]
----
{
  "phenomenonTime": "2026-09-25T16:05:00Z",
  "result": 58.3,
  "Cell": { "@iot.id": "8a394460e407fff" }
}
----

The implementation accepts the request: the Client is accepted, the Observation validates against the schema, the Cell is at level 10, which does not exceed `maxZoneLevel`, and the request contains no coordinates. If the Cell does not exist yet, it is created by reference together with its missing ancestors (<<OGC26-057>>). Because the request contains no FeatureOfInterest, the implementation creates or reuses a FeatureOfInterest whose `feature` is the boundary of the Cell (<<req_dggs_write-zone-level>>).

The data subject receives the Observation as stored (<<req_gdpr_access-right>>). The finest location information the implementation has is the level-10 zone:

[source,http]
----
GET /v1.1/Observations(9d4e2b17-6a3c-4f80-b5e2-1c7a0d9f3e48)?$expand=Cell($select=zoneId,zoneLevel),FeatureOfInterest($select=encodingType,feature)
----

[source,json]
----
{
  "@iot.id": "9d4e2b17-6a3c-4f80-b5e2-1c7a0d9f3e48",
  "phenomenonTime": "2026-09-25T16:05:00Z",
  "resultTime": "2026-09-25T16:05:00Z",
  "result": 58.3,
  "Cell": { "zoneId": "8a394460e407fff", "zoneLevel": 10 },
  "FeatureOfInterest": {
    "encodingType": "application/geo+json",
    "feature": {
      "type": "Polygon",
      "coordinates": [[
        [2.173088, 41.385499], [2.172918, 41.384819], [2.173586, 41.384402],
        [2.174423, 41.384666], [2.174592, 41.385347], [2.173925, 41.385764],
        [2.173088, 41.385499]
      ]]
    }
  }
}
----

=== What other requesters receive

Without an Agreement of the data subject, other requesters receive the Cell association at the public zone level 7 and the FeatureOfInterest as the boundary of that Cell, as shown in the last example of <<clause-dggs>>. The level-10 Cell that the reference materialized, and its ancestors at levels 8 and 9, remain invisible, because no Cell association is released to them at those levels (<<req_dggs_cell-visibility>>). Queries on the fine Cell find nothing (<<req_dggs_query-consistency>>).

[cols="55,15,30",options="header"]
|===
|Request by an unauthenticated requester |Response |Content

|`Observations(9d4e2b17-...)?$expand=Cell`
|200
|`Cell` `87394460effffff` (level 7)

|`Cells('8a394460e407fff')`
|404
|—

|`Cells('87394460effffff')/Observations`
|200
|contains the Observation

|`Observations?$filter=Cell/zoneId eq '8a394460e407fff'`
|200
|empty collection
|===

If the data subject wants registered users to see the measurements at a finer level, for example to help the city identify noisy streets, she creates an Agreement for the Cell association with add:[a ReleaseProfile whose ]`zoneLevel` add:[is ]9 (<<req_dggs_releaseprofile-zone-level>>):

[source,json]
----
{
  "legalBasis": "consent",
  "purpose": "Show my noise measurements to all registered users of this endpoint at street-block level",
  "definition": "https://sta.musterstadt.example/consent/noise-cells/v1",
  "coveredProperties": ["Observation/Cell", "FeatureOfInterest/feature"],
  "permittedOperations": ["publish"],
  "ReleaseProfile": {
    "name": "Registered users at street-block level",
    "audience": "authenticated",
    "zoneLevel": 9
  },
  "Party": { "@iot.id": "6c9e2f70-8a41-4d0b-b3e5-7f1a9c2d8e03" }
}
----

Authenticated requesters then receive the Cell `89394460e43ffff` (level 9, about 0.1 km²) and its boundary as FeatureOfInterest; unauthenticated requesters still receive level 7. No Agreement can release more than level 10, because nothing finer was ever stored.

=== Summary

In this combination, the Accepted Clients conformance class guarantees that only the declared application writes to the Datastream and that it cannot send coordinates or zones finer than level 10. The DGGS conformance class then decides, per requester, at which level the stored zone is released. The precise position exists only in the memory of the smartphone. Should the data subject delete her Party, the Observations are deleted or anonymized according to <<req_gdpr_erasure>> and <<req_dggs_erasure>>; there is no precise location to erase.

== Introduction

The SensorThings API Extension: del:[DGGS] add:[Spatio-temporal Aggregations] 1.0 extends <<OGC18-088>> so that observations can be spatially grouped: an observation linked to a `Cell` del:[directly or indirectly via] add:[through its] `Datastream` or `MultiDatastream` was made somewhere in that cell.

The same `Cell` model can also be used with <<OGC22-022r2>> (STAplus 1.0.1). STAplus adds party, licence, grouping, and related entity types on top of SensorThings. An implementation may therefore deploy DGGS on SensorThings alone, or together with STAplus 1.0.1. The optional <<conformance_class_staplus,STAplus>> Conformance Class applies when STAplus is enabled.

=== Motivation

<<OGC18-088>> already has two spatial concepts. `Location/location` is the geometry of a `Thing`. `FeatureOfInterest/feature` is the geometry of the real-world object or area that was observed. Neither of those geometries answers the question that many dense, opportunistic, or privacy-sensitive observation collections actually ask: *which observations belong together because they occurred somewhere in the same region of a Discrete Global Grid?*

That question is different from “where is the sensor?” and different from “what was observed?”. A mobile contributor may record an observation whose `FeatureOfInterest` is a lake, a street segment, or an unnamed phenomenon, while the only spatial statement that can honestly be made about the observation itself is that it happened *somewhere in this cell*. The same statement applies when coordinates are deliberately coarsened, when many independent observers contribute to the same area, or when a client wants a stable spatial key that does not depend on administrative boundaries.

A Discrete Global Grid System, as specified in <<OGC20-040r3>>, partitions the Earth into a hierarchy of zones. Each zone has a compact identifier, a resolution (zone level), and exactly one parent at the next coarser level. Grouping observations by those zones gives SensorThings a spatial index that is uniform, hierarchical, and independent of `Location/location` and of `FeatureOfInterest/feature`. The optional `Cell/boundary` property is the geometry of that zone. It uses the same encoding rules as `Location/location` and `FeatureOfInterest/feature`.

This extension therefore adds the `Cell` entity as that spatial grouping. del:[Linking an `Observation` to a `Cell` means: this observation belongs somewhere in this cell.] Linking a `Datastream` or a `MultiDatastream` to a `Cell` means: the observations of that stream are grouped in this cell. add:[An `Observation` is not linked to a `Cell` directly. The `Cell` of an observation is the `Cell` of its `Datastream` or `MultiDatastream`. For a moving sensor, the location at which an observation was made is recorded with the `FeatureOfInterest` of the observation, as specified in <<OGC18-088>>. <<annex-moving-sensor>> stores such a ride as one `Datastream` per zone.] The parent/children association on `Cell` makes the DGGS hierarchy navigable with the same REST binding as the rest of the SensorThings API.

=== Data model

The UML diagrams in <<annex-b>> show the del:[DGGS] add:[Spatio-temporal Aggregations] 1.0 data model connected to `Datastream` and to `MultiDatastream`. The `Cell` entity has:

- **zoneId**: the string representation of the cell identifier in the deployed grid system. The value is identical to `@iot.id`. For H3 this is the hexadecimal index. For Geohash this is the geohash string. `@iot.id` is always a CharacterString so that a JavaScript client can parse it without loss of precision.
- **zoneLevel**: the hierarchical resolution of the zone. This property is optional in the data model because some grid systems encode the level in the identifier (for example the length of a Geohash).
- **system**: the identifier of the deployed add:[discrete global] grid system (for example `H3` or `GEOHASH`).
- **boundary**: the geometry of the DGGS zone. It uses the same encoding rules as `Location/location` and `FeatureOfInterest/feature` in <<OGC18-088>>.
- **encodingType**: the encoding type of `boundary`, as used for `Location/location` and `FeatureOfInterest/feature` in <<OGC18-088>>.
- **properties**: optional application-specific annotations.

A `Cell` has zero-or-one `Parent` and zero-to-many `Children`. del:[An `Observation`, a `Datastream`, and a `MultiDatastream` each have] add:[A `Datastream` and a `MultiDatastream` each have] zero-or-one `Cell`. add:[An `Observation` has no direct association to `Cell`.]

=== Uniform cells

A DGGS is useful only if every cell with a given identifier is the same zone of the same system at the same level. If clients were free to create, update, or delete `Cell` entities with arbitrary properties, two observations could be linked to the same `@iot.id` and still mean different zones. del:[The <<conformance_class_cell,Cell>> Conformance Class therefore limits Create, Update, and Delete of a `Cell` to the implementation itself and to an administrator.] add:[The <<conformance_class_cell,Cell>> Conformance Class therefore provides that a client cannot create, update, or delete a `Cell`.]

=== Aggregation

Once observations are grouped by cell, an implementation can calculate summary values for each cell and for every coarser parent. The <<conformance_class_aggregation,Aggregation>> Conformance Class defines that behaviour without prescribing a storage architecture.

The implementation is configured with a set of aggregate intervals and with the zone levels at which each interval applies. Short intervals typically apply to fine cells. Long intervals typically apply to coarse cells.

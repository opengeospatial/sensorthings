[appendix,obligation="normative"]
== Conformance Class Abstract Test Suite

This normative section defines the STAplus 1.0 Conformance Class tests.

[NOTE]
A STAplus compliant implementation must also be compliant with the SensorThings API conformance as defined in <<OGC15-078r6>>, respectively <<OGC18-088>>.

=== STAplus *Core* Conformance Class Tests

=== STAplus *Create* Conformance Class Tests

[conformance_test]
====
[%metadata]
identifier:: {identifier}/conf/create/http
target:: {identifier}/conf/create

target:: {identifier}/req/create/entity
target:: {identifier}/req/create/link-to-existing-entities
target:: {identifier}/req/create/deep-insert
target:: {identifier}/req/create/deep-insert-status-code


test-purpose:: To verify that the service implementation supports the creation of entities as defined in this Standard.
test-method:: For each STAplus entity:

part:: Create an entity instance by following the integrity constraints and creating the related entities with a single request (__i.e.__, deep insert), check if the entity instance is successfully created and the implementation responds as defined in this Standard.

part:: Create an entity instance and its related entities with a deep insert request that does not conform to the Standard (e.g., missing a mandatory property), check if the service fails the request without creating any entity within the deep insert request and responds with the appropriate HTTP status code.


part:: Issue an entity creation request that does not follow the integrity constraints with deep insert, check if the service fails the request without creating any entity within the deep insert request and responds with the appropriate HTTP status code.


part:: Create an entity instance by linking to existing entities with a single request, check if the server responds as defined in this Standard.


part:: Create an entity instance that does not follow the integrity constraints by linking to existing entities with a single request, check if the server responds as defined in this Standard.
====

test-purpose:: To verify that the user's identifier is permanent and unique.

====


[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/authentication/id-create
target:: {identifier-corrigendum}/conf/authentication

target:: {identifier-corrigendum}/req/authentication/id-create


test-purpose:: To verify that the identifier value stored in `Party/authId` is the value set by the authentication.
test-method:: For a non-existing `Party` entity:

part:: Submit an HTTP POST request to create a `Party` entity where the `authId` is not set.
part:: Observe the response to find the location URI for the created `Party` entity.
part:: Issue an HTTP GET request to the location URI and verify that the `Party/authId` is set with the unique identifier that represents the user.
part:: Issue an HTTP GET request to the location URI and verify that `Party/@iot.id` is a random identifier that is not correlated to the user identification.

part:: Submit an HTTP POST request to create a `Party` entity where the `authId` is set with some value.
part:: Observe the response status code and verify it is 400.

====

[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/authentication/id-read
target:: {identifier-corrigendum}/conf/authentication

target:: {identifier-corrigendum}/req/authentication/id-read


test-purpose:: To verify that the `Party/authId` is not exposed except to the `Party` that represents the requesting user.
test-method:: Verify the following:

part:: Construct an HTTP GET request to a `Party` entity that does not represent the requesting user and verify that the `authId` is not contained in the response.
part:: Construct an HTTP GET request to the `Party` entity that represents the requesting user and verify that the `authId` is contained in the response.

test-method:: add:[If the implementation claims MQTT Subscribe STA v1.0 or MQTT Subscribe STA v1.1:]

part:: add:[Subscribe to a `Party` entity that does not represent the MQTT client and verify that the MQTT payload does not contain `authId`.]
part:: add:[If the MQTT client is authenticated as the user represented by a `Party`, subscribe to that `Party` and verify that the MQTT payload contains `authId`.]
====

[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/authentication/id-update
target:: {identifier-corrigendum}/conf/authentication

target:: {identifier}/req/authentication/id-update

test-purpose:: To verify that a user can *not* update the identifier stored in `Party/authId`.
test-method:: Verify that changing the `authId` is not possible for the user itself:

part:: Have the user authenticate and identify the corresponding `Party`.
part:: Construct an HTTP PATCH request to that **same** `Party` entity where the `authId` is set with some value.
part:: Issue an HTTP GET request to that `Party` and verify that the value of the `authId` has not changed.

test-method:: Verify that changing the `authId` is not possible for any other user:

part:: Have the user authenticate and identify the corresponding `Party`.
part:: Construct an HTTP PATCH request to *another* existing `Party` entity where the `authId` is set with some value.
part:: Issue an HTTP GET request to that other `Party` and verify that the value of the `authId` has not changed.
====

[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/authentication/id-delete
target:: {identifier-corrigendum}/conf/authentication

target:: {identifier}/req/authentication/id-delete

test-purpose:: To verify that a user can *not* delete the identifier stored in `Party/authId`.
test-method:: Verify that deleting the `authId` is not possible for the user itself:

part:: Have the user authenticate and identify the corresponding `Party`.
part:: Construct an HTTP PATCH request to that **same** `Party` entity that omits or nulls the `authId`.
part:: Issue an HTTP GET request to that `Party` and verify that the `authId` is still set.

test-method:: Verify that deleting the `authId` is not possible for any other user:

part:: Have the user authenticate and identify the corresponding `Party`.
part:: Construct an HTTP PATCH request to *another* existing `Party` entity that omits or nulls the `authId`.
part:: Issue an HTTP GET request to that other `Party` and verify that the `authId` is still set.
====

add:[These tests belong to the Business Logic Conformance Class. They are specified after the last original abstract test of STAplus 1.0 so that existing abstract test numbers remain unchanged.]

[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/business-logic/gdpr-note
target:: {identifier-corrigendum}/conf/business-logic

target:: {identifier-corrigendum}/req/business-logic/gdpr-note

test-purpose:: add:[To verify that the advertised Business Logic includes the personal-data note.]
test-method:: add:[On the service root URI, find the JSON object with name `{identifier-corrigendum}/conf/business-logic` and follow the link provided in the `href` property. Verify that the loaded HTML page states the following:]

part:: add:[This Standard does not determine which entities or properties are personal data.]
part:: add:[The operator of the endpoint is responsible for identifying personal data and for their lawful processing.]
part:: add:[Lawful processing is achieved by access control, by a legal basis determined by the operator, or by both.]
part:: add:[Access control and lawful processing apply to HTTP operations and to MQTT publish and subscribe.]
part:: add:[A `Party` entity is deleted only when `REMOTE_USER` is identical to that `Party/authId`. An HTTP DELETE of a `Party` is rejected when that condition is not met.]
part:: add:[Claiming this Conformance Class does not constitute GDPR compliance of the deployment.]
====

[conformance_test]
====
[%metadata]
identifier:: {identifier-corrigendum}/conf/business-logic/attribution
target:: {identifier-corrigendum}/conf/business-logic

target:: {identifier-corrigendum}/req/business-logic/attribution

test-purpose:: add:[To verify that the advertised Business Logic includes the License attribution note for creator identification when `License/definition` identifies an attribution license.]
test-method:: add:[On the service root URI, find the JSON object with name `{identifier-corrigendum}/conf/business-logic` and follow the link provided in the `href` property. Verify that the loaded HTML page states the following:]

part:: add:[`License` entities created by the implementation are templates and are read-only.]
part:: add:[When `License/definition` does not identify an attribution license, the template is associated as-is with no party-specific instance and no `attributionText`.]
part:: add:[When `License/definition` identifies an attribution license, each use is a party-specific instance of the template with a non-empty `attributionText`.]
part:: add:[The writable properties of that instance are `attributionText` and `description`, and the associated `Party` may update them.]
part:: add:[Creator identification is always that `attributionText`. `Party/displayName` and `Party/authId` are not used as creator identification.]
part:: add:[A template does not store a party-specific name.]
part:: add:[For an aggregate `MultiDatastream` whose license requires attribution, contributors whose source license requires attribution are identified by reference to those source `License` instances, not by copying their `attributionText`.]
part:: add:[Lawful processing of `attributionText` used as creator identification is the operator's responsibility.]

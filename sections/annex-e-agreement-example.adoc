== Example of the Agreement entity type

=== General

This annex illustrates the life cycle of `Agreement` add:[and `ReleaseProfile` ]entities (<<clause-gdpr>>) for a single data subject, Jane, who contributes air-quality observations to the STAplus endpoint of the fictitious city of Musterstadt, for example with the application of <<annex-accepted-clients-example>>. All names, identifiers and URLs are fictitious.

Jane gives three Agreements:

. to store her display name and show it to registered users;
. to publish the precise position of her sensor to everyone during a measurement campaign that starts later; and
. to store and publish the attribution text of her CC BY licence, signed with a key of her decentralized identifier.

The example then shows what different requesters receive, how Jane reviews her Agreements, which requests the implementation rejects, del:[and ]what happens when Jane withdraws an Agreementadd:[, and how a privacy area protects her home whatever she agrees to].

=== Agreement 1: display name, created by deep insert

A display name is direct personal data. It may only be stored if an Agreement for `Party/displayName` with the operation `store` is effective at the completion of the request (<<req_gdpr_store-direct>>). Jane therefore creates her Party and the Agreement in one request. The implementation sets `authId` from the authentication of the request (STAplus Authentication conformance class).add:[ Because the Agreement permits `publish`, it needs a ReleaseProfile that states to whom the name is released (<<req_gdpr_agreement-relations>>); Jane creates it by deep insert as well.]

[[example-agreement-deep-insert]]
.Creation of a Party together with an Agreement for the display name
[source,http]
----
POST /v1.1/Parties
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...
Content-Type: application/json
----

[source,json]
----
{
  "role": "individual",
  "displayName": "Jane D.",
  "Agreements": [
    {
      "name": "Show my display name",
      "legalBasis": "consent",
      "purpose": "Show my display name to all registered users of this endpoint, next to my air-quality contributions",
      "definition": "https://sta.musterstadt.example/consent/display-name/v2",
      "coveredProperties": ["Party/displayName"],
      "permittedOperations": ["store", "publish"],
      "ReleaseProfile": { "name": "Registered users", "audience": "authenticated" }
    }
  ]
}
----

The same request without the `Agreements` member is rejected with HTTP 409, and neither the Party nor the display name is stored. Jane could instead create the Party without `displayName` and add the name later, after creating the Agreement.

The implementation creates the Agreement with a random identifier that is not correlated to Jane's user identification, and sets `grantedTime` and `status`. Because the request does not contain `effectiveTime`, the implementation sets it to `grantedTime`, and the Agreement is effective immediately (<<req_gdpr_agreement-create>>):

=== Variant: release only through one application

If the endpoint claims the Accepted Clients conformance class, Jane can restrict Agreement 1 to the AirBuddy application of <<annex-accepted-clients-example>> (<<req_accepted-clients_client-restricted-agreements>>). Because Agreements add:[and ReleaseProfiles ]are immutable, she creates a new Agreement add:[with a new ReleaseProfile that names the application ]and withdraws Agreement 1:

[source,json]
----
{
  "name": "Show my display name in AirBuddy",
  "legalBasis": "consent",
  "purpose": "Show my display name to registered users of the AirBuddy app",
  "definition": "https://sta.musterstadt.example/consent/display-name-airbuddy/v1",
  "coveredProperties": ["Party/displayName"],
  "permittedOperations": ["store", "publish"],
  "ReleaseProfile": {
    "name": "Registered users of AirBuddy",
    "audience": "authenticated",
    "clientIds": ["airbuddy-mobile"]
  },
  "Party": { "@iot.id": "6c9e2f70-8a41-4d0b-b3e5-7f1a9c2d8e03" }

----

A registered user who reads through any accepted release of AirBuddy receives "`Jane D.`"; the same user reading through another application, and any unauthenticated requester, receives the Party without `displayName`. If the operator revokes AirBuddy, the display name is no longer released through it. The purpose now describes exactly what the implementation enforces. <<annex-client-restricted-agreement-example>> shows in detail how such an Agreement is evaluated.

=== Agreement 2: precise position, for the period of a campaign

Positions and times are indirect personal data. They are always stored, but released to others only in generalized form unless an Agreement authorizes the release of the stored value (<<req_gdpr_release-location>>). The city runs a four-week measurement campaign from 1 October to 29 October 2026. On 25 September, Jane agrees that everyone may see the precise position of her sensor for the duration of that campaign. The city wants to compare her readings with its official monitoring stations, but the Agreement cannot restrict the release to the city: with del:[`audience` `public`] add:[a ReleaseProfile whose `audience` is `public`], the position is available to every requester, and the purpose says so (see the NOTE after <<tab-relations-to-agreement>>). She sets `effectiveTime` to the start and `expiryTime` to the end of the campaign. The operation is `publish` only, because storage of indirect personal data needs no Agreement.

[[example-agreement-location]]
.Agreement for the release of precise positions until a given time
[source,http]
----
POST /v1.1/Parties('6c9e2f70-8a41-4d0b-b3e5-7f1a9c2d8e03')/Agreements
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...
Content-Type: application/json
----

[source,json]
----
{
  "name": "Precise sensor position during the autumn campaign",
  "legalBasis": "consent",
  "purpose": "Publish the exact position of my PM2.5 sensor to everyone during the autumn measurement campaign",
  "definition": "https://sta.musterstadt.example/consent/precise-location/v1",
  "coveredProperties": ["Location/location", "FeatureOfInterest/feature"],
  "permittedOperations": ["publish"],
  "ReleaseProfile": { "name": "Everyone", "audience": "public" },
  "effectiveTime": "2026-10-01T00:00:00Z",
  "expiryTime": "2026-10-29T00:00:00Z"
}
----

The Agreement exists from 25 September on, but it is effective only from 1 October until 29 October (<<req_gdpr_agreement-effective>>). Before and after that period, positions are released in generalized form, without any action by Jane. The implementation would reject an `effectiveTime` before the time of the request, or an `expiryTime` that is not later than `effectiveTime`, with HTTP 400 (<<req_gdpr_agreement-create>>). Jane can withdraw the Agreement at any time, also before the campaign starts.add:[ The implementation stores the deep-inserted ReleaseProfile "`Everyone`" with the identifier `9a2e7c15-3b48-4f0d-8c61-5e7a2d9b0f34`; further Agreements can refer to it.]

The client lets Jane sign the Agreement with a key of her decentralized identifier and sends the signature as `proof` (<<rec_gdpr_proof>>).add:[ The Agreement refers to the ReleaseProfile "`Everyone`" created with Agreement 2.]

=== Withdrawal

Jane decides that registered users should no longer see her name. She withdraws Agreement 1 (<<req_gdpr_agreement-withdrawal>>):

[source,http]
----
PATCH /v1.1/Agreements('b7e2c1a0-4f53-4d7e-9a61-2f0c8d4e9f11')
Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6ImF0K2p3dCJ9...
Content-Type: application/json
----

[source,json]
----
{ "status": "withdrawn" }
----

The implementation sets `withdrawalTime`. Because no Agreement for `Party/displayName` with the operation `store` remains effective, it erases the display name before it sends the response (<<req_gdpr_store-direct>>). From that response on, no HTTP response and no MQTT message contains the name.

[source,json]
----
{
  "@iot.id": "b7e2c1a0-4f53-4d7e-9a61-2f0c8d4e9f11",
  "name": "Show my display name",
  "legalBasis": "consent",
  "purpose": "Show my display name to all registered users of this endpoint, next to my air-quality contributions",
  "definition": "https://sta.musterstadt.example/consent/display-name/v2",
  "coveredProperties": ["Party/displayName"],
  "permittedOperations": ["store", "publish"],
  "grantedTime": "2026-09-25T10:02:11Z",
  "effectiveTime": "2026-09-25T10:02:11Z",
  "status": "withdrawn",
  "withdrawalTime": "2026-11-02T08:41:27Z"
}
----

The withdrawn Agreement remains visible to Jane as a record of her earlier consent.add:[ Its ReleaseProfile "`Registered users`" is no longer used by an active Agreement; Jane can delete it or keep it for a later Agreement.] If she had withdrawn it with HTTP DELETE instead, it would no longer be visible to her, and any record the operator keeps to demonstrate the earlier consent would be declared in the privacy notice.

Had Jane withdrawn only the `publish` part of her consent, she would instead create a new Agreement for `Party/displayName` with `permittedOperations` `["store"]` and then withdraw Agreement 1: the name would remain stored and visible to Jane, but would no longer be released to others.

=== Free text of a Thing

Jane also registers her sensor with a general-purpose SensorThings client that lets her type a name and a description. The implementation stores the text without an Agreement, but does not release it to others (<<req_gdpr_release-free-text>>):

[source,json]
----
{
  "name": "Jane's balcony sensor",
  "description": "PM2.5 sensor on my balcony, Lindenweg 5, 3rd floor",
  "properties": { "mounting": "balcony railing, facing the street" },
  "Party": { "@iot.id": "6c9e2f70-8a41-4d0b-b3e5-7f1a9c2d8e03" }
}
----

Jane receives the Thing as submitted. Any other requester receives the mandatory `name` and `description` as empty strings, and no `properties`:

[source,json]
----
{
  "@iot.id": 102,
  "@iot.selfLink": "https://sta.musterstadt.example/v1.1/Things(102)",
  "name": "",
  "description": "",
  "Locations@iot.navigationLink": "https://sta.musterstadt.example/v1.1/Things(102)/Locations",
  "Datastreams@iot.navigationLink": "https://sta.musterstadt.example/v1.1/Things(102)/Datastreams"
}
----

A query such as `Things?$filter=substringof('Lindenweg',description)` does not find the Thing for other requesters (<<req_gdpr_query-consistency>>). If Jane wants the name to be public, she creates an Agreement with `coveredProperties` `["Thing/name"]`, `permittedOperations` `["publish"]` and del:[`audience` `public`] add:[the ReleaseProfile "`Everyone`"]; the description, which contains her address, stays private. Had she registered the sensor with the AirBuddy application of <<annex-accepted-clients-example>>, name and description would be the fixed values of its WriteProfile, and would be released without an Agreement.

If the implementation claims the Accepted Clients conformance class, Max adds `Datastream/WriteProfile` and `MultiDatastream/WriteProfile`; if it claims the DGGS conformance class, he adds `Observation/Cell`, `Datastream/Cell` and `MultiDatastream/Cell`. Without `zoneLevel`add:[ in the ReleaseProfile], the Cell associations are then released at the stored zone level.

The Agreement refers to property paths, not to individual entities. It therefore applies to everything Max contributes from now on, until he withdraws it; a single withdrawal returns all his data to the defaults of this Profile at once.

Even this Agreement does not release everything:

* `Party/authId` is not Agreement-controlled and is never released to others, because it would allow Max to be tracked across services;
* his Agreements add:[and ReleaseProfiles ]remain visible only to him (<<req_gdpr_agreement-access>>add:[, <<req_gdpr_releaseprofile-lifecycle>>]);
* `License/attributionText` is released, but still cannot be used in `$filter` or `$orderby` (<<req_gdpr_attribution-filter>>); and
* `Observation/result` and `Observation/parameters` are not controlled by Agreements at all; the privacy notice declares how they are released.

A consent of this breadth is valid only if it is specific and informed (GDPR Articles 4(11) and 7(2)). The document referenced by `definition` therefore has to state plainly that the consent includes the display name, free texts and the exact positions and times of all contributions, and that they are published to everyone. The client must not offer this Agreement as a default or as a precondition for contributing, and withdrawing it, with a single HTTP PATCH or DELETE, must be as easy as giving it. If the contributions can contain special categories of personal data, `legalBasis` has to be `explicit-consent`.

The list of property paths is fixed by the version of this Profile and of the conformance classes that the endpoint implements. A later version that adds property paths does not extend an existing Agreement; the contributor has to create a new one.

== Requirements Class Accepted Clients

=== Overview

The Accepted Clients requirements class lets the operator of an endpoint know which software writes to the endpoint and what that software is allowed to write. It adds two entity types:

* `Client`: an application release that the operator has accepted, identified by its client identifier together with its software version, its software identifier, or both, for example the OAuth 2.0 `client_id` (<<RFC6749>>) and the `software_version` and `software_id` (<<RFC7591>>); and
* `WriteProfile`: the declared and enforced write behaviour of one or more Clients: which entity types, ObservedProperties and observation types they may write, and JSON Schemas (<<JSONSchema>>) that every written entity has to satisfy, including `result`, `parameters`, `properties`, `name` and `description`.

Each endpoint keeps its own catalog of Client and WriteProfile entities. The catalog is public: any requester can read it through the SensorThings API. Only catalog administrators appointed by the operator can change it.

The implementation resolves, from the single credential presented with each create or update request, both the principal (a user or, for a Party whose `role` is `institutional` or `system`, the organisation or system) and the client release, and accepts the request only if the catalog contains an accepted Client with an identical client identifier and an identical software version or software identifier. There are no version ranges: every accepted release is a separate Client entity. Every Datastream and MultiDatastream is bound, at creation, to the WriteProfile under which it was created. This provenance cannot be changed, and only Clients that implement that WriteProfile can add observations to it.

Requests with which data subjects exercise their rights (deletion, creation and withdrawal of Agreements, rectification) are exempt, so that the catalog can never prevent a data subject from exercising a GDPR right.

=== Entity type WriteProfile

A WriteProfile describes the write behaviour that one or more Clients have declared and that the implementation enforces. Several releases of the same application can implement the same WriteProfile; a new WriteProfile is needed only when the write behaviour changes. Because Datastreams and MultiDatastreams are bound to a WriteProfile, a WriteProfile cannot be changed after creation; it can only be superseded.

The `entitySchemas` are the enforcement mechanism for content that the implementation cannot otherwise interpret. For example, a schema for `Observation` can restrict `result` to a number range and `parameters` to a closed set of members, and a schema for `Datastream` can restrict `name` and `description` to an enumeration or a pattern. `resultCategory` and `clientSideProcessing` are declarations that make the behaviour of the Client transparent to data consumers and data subjects.add:[ The properties of a WriteProfile control what is stored; the conditions under which stored values are released to others are the properties of the ReleaseProfiles of the data subject (<<clause-gdpr>>).] `freeTextPolicy` is verified: for `none` and `controlled-vocabulary`, the implementation checks when the WriteProfile is created that its schemas admit no free text (<<req_accepted-clients_free-text-policy>>). Names, descriptions and properties written under such a WriteProfile are not the text of a user and are released without an Agreement of the data subject; text written under `moderated` or `free` is released only with an Agreement (<<req_gdpr_release-free-text>>).

=== Client acceptance and write enforcement

The identification relies on a single credential that resolves to both the principal and the client release. How the implementation resolves it is not specified. With OAuth 2.0, the implementation reads `client_id` from a JWT access token (<<RFC9068>>) or obtains it by token introspection (<<RFC7662>>); `software_id` and `software_version` are client metadata defined in <<RFC7591>>, which the authorization server adds to the token or the introspection response, or which the implementation obtains from the client registration. With a credential registered by the operator, such as an API key or a local account used with HTTP Basic authentication, the implementation looks up the principal and the Client to which the credential is bound. For an autonomous system, the principal and the client can be the same software; the OAuth 2.0 client credentials grant, whose access token has the client as subject, is an example. In every case, the client identification comes from the binding made by the issuer of the credential, never from other parts of the request such as a `User-Agent` header. How strongly the client identifier is bound to the actual software depends on how the client proves its identity to the issuer (see <<rec_accepted-clients_client-authentication>>).

Things, Locations and FeaturesOfInterest can be created without a Datastream. Such an entity is accepted if any WriteProfile of the Client permits it. A Client with several WriteProfiles could therefore create a Location with precise coordinates, or a Thing with free text, under a lenient WriteProfile and later link it to a Datastream whose WriteProfile does not permit it. The implementation therefore checks each entity again when it is linked: an entity has to conform to every WriteProfile that governs it through the Datastreams and Observations it is associated with. The check applies in both directions, when a Location or FeatureOfInterest is linked to a governed Thing or Observation, and when a Datastream is created on an existing Thing.

include::../requirements/accepted-clients/REQ011a_link-conformance.adoc[]

NOTE: Because an entity has to conform to every WriteProfile that governs it, the stricter WriteProfile always prevails. This has two consequences. First, a Thing cannot carry Datastreams of two applications whose WriteProfiles contain conflicting schemas for Thing, for example two different constant values for `name`; each application then uses its own Thing, which corresponds to the usual modelling of one Thing per device or application. Catalog administrators who want applications to share Things should accept only WriteProfiles whose schemas for Thing, Location and FeatureOfInterest are compatible. Second, a later application can never loosen what an earlier one has declared: once a Thing carries a Datastream bound to a WriteProfile with `locationPolicy` `cell-only` (<<clause-dggs>>), it cannot be associated with a precise Location, even by an application whose own WriteProfile permits precise positions.

=== Provenance and personal data

The application that a person uses to contribute can itself reveal information about the person, for example the use of a health application. The association of a Datastream or MultiDatastream with its WriteProfile is therefore part of the personal data register (<<tab-register>>) and released to others only with an Agreement. The catalog itself contains no personal data: the provider of an application is an institutional Party.

=== Agreements restricted to applications

An Agreement of the GDPR requirements class releases a value to every requester of del:[its `audience`] add:[the `audience` of its ReleaseProfile], whatever application the requester uses. With the client catalog, a data subject can restrict the release further to named applicationsadd:[ by the ReleaseProfile property `clientIds`], for example "`show my display name to registered users of the AirBuddy app`". The implementation then resolves the client identification also for read requests and releases the value only if the request comes through one of the listed applications.

The del:[Agreement] add:[ReleaseProfile] refers to client identifiers, not to Client entities. A Client entity describes one release, whereas a data subject agrees to an application; an Agreement that referenced a release would stop being effective with the next release. Because del:[Agreements are] add:[ReleaseProfiles are] immutable, the reference to the application keeps the Agreement valid across releases, and the status of the Client entities decides whether a release is currently trusted.

NOTE: A restriction to applications controls to which applications the implementation releases a value, not what those applications do with it. The provider of a listed application becomes a recipient of the value; the privacy notice (GDPR Article 13(1)(e)) and the terms of the application need to cover this. The restriction is only as strong as the identification of the client: a public client without attestation can be impersonated by other software that uses its client identifier (see <<rec_accepted-clients_client-authentication>>).

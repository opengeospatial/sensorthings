=== Changes in draft 0.2

All changes relative to draft 0.1 are marked in the AsciiDoc source with `\add:[\]` and `\del:[\]`.

* New optional conformance class Party Context (<<clause-party-context>>) with the requirements `register`, `release`, `association-release`, `write`, `query-consistency`, `privacy-notice` and `business-logic`, the recommendation `observer-position`, and the corresponding abstract tests. It applies this Profile to the `PartyLocation` and `PartyActivity` entity types of OGC 26-040 (STAplus Party Context 1.0)del:[, which replaces the GDPR and Sharing conformance classes of the former STAplus 1.1 draft].
* Observer context is never generalized, also not with the DGGS conformance class: it is released with its stored values on the basis of an effective Agreement, or withheld completely.
* OGC 26-040 has no normative reference to this Profile. It accepts observer context of individual parties only with a Business Logic statement of the rules that apply; <<req_party-context_business-logic>> provides that statement, and <<req_gdpr_personal-data-register>> requires an implementation of OGC 26-040 that accepts individual parties to implement the Party Context conformance class.
* New requirement <<req_gdpr_retention>>: mandatory advertised `retentionPeriod` (default and per entity type) for all entities attributable to an individual Party except the Party and its Agreements; on expiry the implementation applies the deletion or anonymization declared for <<req_gdpr_erasure>>; observer context is always deleted; `retentionTime` of observer context can only shorten the period; optional `inactivityPeriod` for erasing inactive Parties. Item (f) of <<req_gdpr_privacy-notice>>, <<req_gdpr_erasure>>, the GDPR settings table, Annex C and the JSON examples are updated.
* Personal data register: rows for `PartyLocation`, `PartyActivity` and the Observation associations (Party Context only); attributable rule (9) in <<req_gdpr_personal-data-register>>.
* del:[`Agreement/audience` value `recipients` and the association `Recipients` (<<req_gdpr_agreement-relations>>, <<req_gdpr_agreement-create>>, <<req_gdpr_agreement-immutable>>, <<req_gdpr_agreement-effective>>).] add:[`audience` value `recipients` and the association `Recipients`, both of the ReleaseProfile (<<req_gdpr_releaseprofile-relations>>, <<req_gdpr_agreement-effective>>).]
* <<req_gdpr_agreement-effective>>: a Campaign-bound Agreement also covers the observer context of the campaign's observations.
* <<req_dggs_write-zone-level>>: `locationPolicy` `cell-only` also rejects `PartyLocation/position`.
* Annex C mapping rows and the example in <<annex-party-context-example>>.
* add:[Annex B: titles for Figures B.1 and B.2 (data model connected to Datastream and to MultiDatastream).]
* add:[New entity type `ReleaseProfile` (<<req_gdpr_releaseprofile-properties>>, <<req_gdpr_releaseprofile-relations>>, <<req_gdpr_releaseprofile-lifecycle>>), owned by the data subject, immutable and visible only to the data subject. It collects all conditions of read access: `audience` and `Recipients`, `clientIds` (Accepted Clients), `zoneLevel` and `privacyZones` (DGGS), and the new `locationResolution`, `timeResolution` and `privacyAreas`. The Agreement keeps the legal record (legal basis, purpose, definition, covered properties, operations, validity, status, proof, Campaign) and is associated with exactly one ReleaseProfile if it permits `publish`. `audience` is removed from the Agreement; `clientIds` (<<req_accepted-clients_client-restricted-agreements>>) and `zoneLevel`/`privacyZones` (<<req_dggs_releaseprofile-zone-level>>, formerly `/req/dggs/agreement-zone-level`) move to the ReleaseProfile.]
* add:[Spatial and temporal obfuscation chosen by the data subject, also without the DGGS conformance class. New requirement <<req_gdpr_release-resolution>>: the release resolution of a location or time value is the smallest resolution granted by the ReleaseProfiles of the effective Agreements, capped by the public generalization, and raised by privacy areas. New requirement <<req_gdpr_privacy-areas>>: the privacy areas of all ReleaseProfiles of a Party restrict every release of the Party's locations and times from the creation of the ReleaseProfile until its deletion, independent of Agreements; a privacy area without `area` sets a global minimum. <<req_gdpr_release-location>> and <<req_gdpr_release-time>> use the release resolution and require nested partitions and durations. DGGS privacy zones are properties of ReleaseProfiles as well (<<req_dggs_privacy-zones>>). Observer context to which a privacy area or zone or a resolution applies is withheld (<<req_party-context_release>>).]
* add:[New requirement <<req_accepted-clients_write-location-resolution>>: the optional WriteProfile property `storedLocationResolution`, which makes the implementation generalize written positions before storing them. WriteProfiles control what is stored; ReleaseProfiles control what is released.]
* add:[Clause 5: abstract tests that create "an Agreement with `audience` ..." create a ReleaseProfile with these properties. Abstract tests, Clauses 6 to 9a, Annex C and the examples in Annexes D to H and in `code/examples` are updated. Changes inside JSON listings cannot carry change marks.]
* add:[`STAplus10X.xml`: new class ReleaseProfile with the attributes `name`, `description`, `audience`, `locationResolution`, `timeResolution`, `privacyAreas`, `zoneLevel`, `privacyZones` and `clientIds`, and the associations Party–ReleaseProfile (1 to 0..*), Agreement–ReleaseProfile (0..* to 0..1) and ReleaseProfile–Party (`recipients`, navigable only from the ReleaseProfile); `audience`, `zoneLevel`, `privacyZones` and `clientIds` removed from Agreement; code list AgreementAudienceCode renamed ReleaseAudienceCode with the new value `recipients`; data types Number and TM_Duration; attribute `storedLocationResolution` added to WriteProfile; the diagram "STAplus GDPR Profile Entities" shows the new class and associations.]
* Build: `accept_changes.rb` and the link `26-055-diff.adoc` for the change-marked and the clean build.
* add:[Consistency review of 2026-09-30: the identifier of the ObservedProperties conformance class of OGC 26-057 in <<tab-dggs-dependencies>> is corrected to `/conf/observed-properties`; a misplaced duplicate part of <<req_dggs_privacy-zones>> is removed; <<req_gdpr_mqtt>> applies to every MQTT delivery of entity changes, including the MQTT Subscribe classes of OGC 26-040 and the SensorThings MQTT capability, not only to the STAplus MQTT Subscribe classes; <<req_party-context_business-logic>> and <<req_party-context_privacy-notice>> distinguish the legal basis for storing observer context (declared in the privacy notice) from the legal basis for releasing it (the effective Agreement); <<req_gdpr_retention>> requires the Business Logic to state the deletion of Parties after `inactivityPeriod`, so that the personal-data note of STAplus 1.0.1 remains accurate. Abstract tests are updated accordingly. The GDPR Requirements Class inherits the Relation Requirements Class of STAplus 1.0.1. The personal data register covers `Campaign/termsOfUse`, `Campaign/privacyPolicy`, `Campaign/url`, `Campaign/creationTime`, `Campaign/startTime`, `Campaign/endTime`, `ObservationGroup/termsOfUse` and `ObservationGroup/privacyPolicy`. The requirement `/req/party-context/party-role` of OGC 26-040 is now part of its Create Conformance Class. The landing-page settings of OGC 26-057 are read from the JSON object named with its Landing Page Conformance Class URI. <<OGC18-088>> is dated 2021. <<req_dggs_cell-visibility>> no longer exempts Cells created by the implementation for entities of non-individual Parties, because OGC 26-057 does not record for which entity a Cell was created. <<req_gdpr_access-right>> yields to <<req_gdpr_retention>>.]

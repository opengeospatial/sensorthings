== Conformance

All requirements-classes and conformance-classes described in this document are owned by the standard(s) identified.

=== Introduction

The OGC SensorThings API extension: DGGS 1.0 is an extension of <<OGC18-088>>. An implementation that claims conformance to this Standard SHALL also conform to the Sensing data model of <<OGC18-088>>. An implementation MAY also conform to <<OGC22-022r2>> or <<OGC26-040>>. Those STAplus Standards are required only if the implementation claims the <<conformance_class_staplus>> Conformance Class.

This Standard adds the `Cell` entity type to the SensorThings data model. The `Cell` Conformance Class defines the data model extension. The mandatory `Landing Page` Conformance Class requires the implementation to advertise the deployed grid system in the `serverSettings` object on the landing page, as specified for extensions in <<OGC18-088>> §9.2.1, to advertise a Polygon or MultiPolygon that defines the area within which a `Cell` can be created, and to advertise each aggregate function with a definition identifier, a well-accepted mathematical equation, and entity linking as specified in <<INSIDE-EntityLinking>>. The `Cell CRUD` Conformance Class defines the Read of `Cell` via HTTP GET and restricts Create, Update, and Delete of a `Cell`. A created `Cell` SHALL be within the advertised cell-create boundary, and anonymous creation is throttled. The `Authentication` Conformance Class exempts authenticated creation of a `Cell` from throttling. The `ObservedProperties` Conformance Class defines how a base `ObservedProperty` is linked to the derived `ObservedProperty` of each aggregate function. Create, Update, and Delete of a derived `ObservedProperty` are limited to the implementation itself and to an administrator. The `Aggregation` Conformance Class defines how an implementation calculates aggregate values from raw observations linked to a cell and publishes those values as `Observation` entities of a `MultiDatastream`. An implementation that claims the `Aggregation` Conformance Class SHALL also conform to the MultiDatastream Requirements Class of <<OGC18-088>>. The optional `STAplus` Conformance Class applies when STAplus is enabled: each aggregate `MultiDatastream` is owned by a `Party` whose `role` is `system`. That `Party` is the producer of the aggregate.

=== DGGS 1.0 Conformance Classes

This OGC Standard defines two mandatory and five optional conformance classes.

Conformance with this Standard shall be checked using all the relevant tests specified in Annex A of this document. The framework, concepts, and methodology for testing, and the criteria to be achieved to claim conformance are specified in the OGC Compliance Testing Policies and Procedures and the OGC Compliance Testing web site.

In order to conform to this OGC Standard, a software implementation shall choose to implement:

* The mandatory conformance classes `Landing Page` and `Cell`;
* Any one of the optional conformance classes; and
* Pass all applicable tests as defined in Annex A of this document.

This is the list of DGGS 1.0 Conformance Classes.

* *Landing Page* (mandatory): This Conformance Class requires the implementation to advertise the deployed grid system (for example H3 or Geohash) and the coarsest and finest zone levels as a JSON object on the landing page, and to advertise a Polygon or MultiPolygon that defines the area within which a `Cell` can be created. It also requires the implementation to advertise each aggregate function (`min`, `max`, `avg`, `stddev`, `count`) with a definition identifier and a well-accepted mathematical equation, and to register entity links as specified in <<INSIDE-EntityLinking>>.

* *Cell* (mandatory): This Conformance Class defines the `Cell` entity, its properties, and its associations with `Observation`, `Datastream`, `MultiDatastream`, and `Cell`. `Cell/@iot.id` is a CharacterString, identical to `zoneId`. The optional `Cell/boundary` property is the geometry of the zone and uses the same encoding rules as `Location/location` and `FeatureOfInterest/feature`.

* *Cell CRUD* (optional): This Conformance Class defines the Read of `Cell` via HTTP GET. It also limits Create, Update, and Delete of a `Cell` to the implementation itself and to an administrator, except that a `Cell` SHALL be created by reference only. A nested object `{"@iot.id": "309f09"}` creates the `Cell` from a template with `zoneId` equal to `"309f09"`. Inline creation of a `Cell` is rejected. A created `Cell` SHALL be within the advertised cell-create boundary. Anonymous creation is throttled (HTTP 429).

* *Authentication* (optional): Authenticated creation of a `Cell` by reference is not throttled. That creation records neither a user identifier nor a `Party`.

* *ObservedProperties* (optional): This Conformance Class defines how a base `ObservedProperty` and the derived `ObservedProperty` of each aggregate function are linked. The definition identifier of the function advertised on the landing page SHALL be linked to the derived `ObservedProperty` that is associated with the corresponding value in the aggregate `MultiDatastream`. Create, Update, and Delete of a derived `ObservedProperty` SHALL be performed only by the implementation itself or by an administrator.

* *Aggregation* (optional): This Conformance Class defines how an implementation calculates aggregate values from raw observations linked to a cell. The implementation is configured with aggregate intervals. Aggregation starts at the finest resolution of the linked cell and visits every parent up to the configured coarsest resolution. Each aggregate function is calculated as advertised on the landing page.

* *STAplus* (optional): This Conformance Class applies when STAplus is enabled. Each aggregate `MultiDatastream` SHALL be owned by a `Party` whose `role` is `system`. That `Party` is the producer of the aggregate. Creator identification follows <<OGC22-022r2>>.

=== Overview

The <<conformance_class_aggregation,Aggregation>> Conformance Class defines how an implementation calculates aggregate values from raw `Observation` entities del:[that are linked to a `Cell`] add:[of a `Datastream` that is linked to a `Cell`]. Aggregation is a SensorThings behaviour. This Standard does not specify a storage architecture, a database product, or an internal job scheduler.

An implementation that claims this Conformance Class also conforms to the del:[MultiDatastream] add:[Datastream and MultiDatastream] Requirements Classes of <<OGC18-088>>.

The implementation is configured with a set of aggregate intervals and with the zone levels at which each interval applies. When a raw observation del:[is linked to a cell] add:[is created in a `Datastream` that is linked to a cell], aggregation starts at that cell (the finest resolution in the request) and visits every parent up to the advertised `coarsestZoneLevel`. For each visited cell and each interval that applies at that zone level, the implementation calculates the aggregate functions advertised on the landing page from the raw observations that contribute to that cell, and publishes the result as an `Observation` of a del:[`MultiDatastream`] add:[`Datastream` or a `MultiDatastream`] that is linked to that `Cell`. add:[A `Datastream` aggregate has one derived `ObservedProperty` and a single `result`.] Each value in a `MultiDatastream` result is linked to the corresponding derived `ObservedProperty`, and that `ObservedProperty` is linked to the function definition advertised on the landing page. add:[A `Datastream` or `MultiDatastream` that is linked to a `Cell` has `observedArea` equal to the `boundary` of that `Cell`.]

NOTE: The Requirements Class in this section is part of the Conformance Class <<conformance_class_aggregation,Aggregation>>.

[%metadata]
identifier:: {identifier}/req/aggregation/intervals

The implementation SHALL be configured with a non-empty set of aggregate intervals. Each interval SHALL be a duration or a calendar period (for example `1min`, `1hour`, `1day`, `1month`, `1year`).

The implementation SHALL be configured with the zone levels at which each interval applies. An interval MAY apply to one or more zone levels. A zone level MAY have del:[zero,] one, or many add:[temporal] intervals.

The implementation SHALL provide a JSON object in the `serverSettings` object on the landing page (the root URI) with the name `{identifier}/conf/aggregation`. That object SHALL contain:

* a property `intervals` whose value is a JSON array of the configured interval identifiers;
* a property `zoneLevels` whose value is a JSON object. Each name is a zone level encoded as del:[a string.] add:[an integer.] Each value is a JSON array of the interval identifiers that apply at that zone level.

[[aggregation-landing-page-functions]]
[requirement]
====
[%metadata]
identifier:: {identifier}/req/aggregation/landing-page-functions

The implementation SHALL provide a JSON object in the `serverSettings` object on the landing page (the root URI) with the name `{identifier}/conf/del:[observed-properties] add:[aggregation]`. That object SHALL contain a property `functions` whose value is a JSON array. The array SHALL contain one object for each of the aggregate functions `min`, `max`, `avg`, `stddev`, and `count`, in that order.

Each object in `functions` SHALL contain:

* a property `id` whose value is the CharacterString `min`, `max`, `avg`, `stddev`, or `count`;
* a property `definition` whose value is a URI that identifies that aggregate function;
* a property `equation` whose value is a CharacterString that is a well-accepted mathematical equation for that function;
* a property `method` whose value is a CharacterString that names the function (for example `MIN`, `MAX`, `AVG`, `STDDEV`, `COUNT`).

The equations SHALL be:

* `min`: the minimum of the contributing numeric results;
* `max`: the maximum of the contributing numeric results;
* `avg`: the arithmetic mean of the contributing numeric results;
* `stddev`: the sample standard deviation of the contributing numeric results, or null if fewer than two results contribute;
* `count`: the number of contributing raw observations.

The `definition` URI of each function SHALL be the identifier that an `ObservedProperty` uses to link to that function, as specified in <<conformance_class_observed_properties,ObservedProperties>>.

[requirement]
====
[%metadata]
identifier:: {identifier}/req/aggregation/functions

For each visited cell and each applicable interval, the implementation SHALL calculate the aggregate functions advertised on the landing page as specified in <<aggregation-landing-page-functions>>, from the numeric raw observation results that contribute to that cell in that interval. The calculation of each function SHALL match the advertised `equation` of that function.

Raw observations that contribute to a cell are the observations del:[linked to that cell and the observations linked to any descendant of that cell] add:[of the `Datastreams` linked to that cell and of the `Datastreams` linked to any descendant of that cell] that fall in the interval. Only observations whose `result` is numeric SHALL contribute. del:[Observations that are not linked to a `Cell`, directly or through their `Datastream`, whose `Datastream` is not linked to a `Cell` SHALL NOT contribute.]
====

[requirement]
====
[%metadata]
identifier:: {identifier}/req/aggregation/traversal

When del:[a raw `Observation` is created or updated with a link to a `Cell`, or when ]a raw `Observation` is created or updated in a `Datastream` that is linked to a `Cell`, the implementation SHALL calculate aggregates for that `Cell` and for every ancestor `Cell` obtained by following `Parent` until the advertised `coarsestZoneLevel`.

Traversal SHALL start at the finest resolution (the del:[linked `Cell`] add:[`Cell` linked to the `Datastream`]) and SHALL visit each parent in turn up to the coarsest resolution. For each visited cell, the implementation SHALL calculate the aggregate functions for every interval that applies at that cell's `zoneLevel`.

del:[If a parent `Cell` does not yet exist, the implementation SHALL materialize it as specified in `{identifier}/req/cell-cud/parent-materialization` before publishing aggregates for that parent.] add:[When the implementation creates an aggregate `Datastream` or `MultiDatastream`, it SHALL follow <<materialize-parents>>. If a parent `Cell` does not yet exist, the implementation SHALL instantiate that parent, and only when that parent is spatially within the cells boundary advertised as specified in <<cells-boundary>>. Each instantiated parent SHALL be linked through the `Parent` association. A `Cell` whose `zoneLevel` is less than or equal to `coarsestZoneLevel` SHALL have no `Parent`.]

[%metadata]
identifier:: {identifier}/req/aggregation/multidatastream

The implementation SHALL publish each aggregate as an `Observation` of a del:[`MultiDatastream`] add:[`Datastream` or a `MultiDatastream`] that is linked to the visited `Cell`.

add:[A `Datastream` that publishes an aggregate SHALL have one derived `ObservedProperty`, the derived property of one advertised aggregate function, and a `Cell` association to the visited `Cell`. del:[That `MultiDatastream`] add:[A `MultiDatastream` that publishes an aggregate] SHALL:

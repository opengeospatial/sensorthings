== Scope
This Standard extends <<OGC22-022r2>> with the `PartyLocation` and `PartyActivity` entity types and with the corresponding associations from `Observation` and `Party`. It also defines the optional `Share` entity so that a party can grant other parties access to a `PartyLocation` or `PartyActivity`. It does not replace STAplus 1.0.1. All STAplus 1.0.1 requirements remain in force unless this Standard explicitly extends them. The service root URI is the SensorThings API service root. This Standard does not change that URI.

The encoding of `PartyLocation/position` follows the Default-CRS, Geometry-FG, and Geometry-WKT rules of <<OGC22-022r2>> as applied to `Location/location` and `FeatureOfInterest/feature`. The supported geometry `encodingType` ValueCodes, including those for `PartyLocation/position`, are advertised on the landing page as specified in the <<conformance_class_landing_page>> Conformance Class. The accepted `PartyLocation` `environment` EnvCodes are advertised on the landing page as specified in that Conformance Class.

=== Security Considerations
The Security Considerations of <<OGC22-022r2>> apply. The `Party` entity still does not store a personal profile. Identity data and the record of a legal basis remain in the authentication system that supplies `Party/authId`, or in another system aligned with that identifier.

STAplus 1.1 adds observer context. `PartyLocation` records where a party was. `PartyActivity` records what the party was doing. Together with time, that information can identify a natural person. The same is true of the SensorThings `Location` and `HistoricalLocation` of a `Thing` owned by a `Party` whose `role` is `individual`. Those records are personal data.

`FeatureOfInterest` is not that kind of record. It has no `Party` association. It is a public resource: a park, a lake, a sampling plot, or another publicly observable feature. It is not the observer's position. If a client would otherwise put the observing user's location into `FeatureOfInterest` geometry, that geometry is null and the position is stored in `PartyLocation`.

When a service accepts individual parties, the GDPR Conformance Class applies (see <<conformance_class_gdpr>>). Access to that personal data is limited to the owner. Another user cannot read, create, update, or delete another party's `Location`, `HistoricalLocation`, `PartyLocation`, or `PartyActivity`. The implementation does not expose those entities through `$expand`, navigation, deep insert, or MQTT. When an entity is deleted, related `Share` records and MQTT retained messages are cleared with it. The owner can delete their context in bulk and can export the entities that belong to them. Optional `retentionTime` on observer context, and a service-wide `retentionPeriod` for historical `Thing` locations, limit how long those records are kept. The owner can set `restricted` on a `PartyLocation` or `PartyActivity` to stop sharing. An observation of an individual party always has a `PartyLocation`, so the observer's position is not mixed with the observed feature.

By default, only the owner sees that personal context. The optional Sharing Party Context Conformance Class (see <<conformance_class_sharing_party_context>>) lets the owner grant named other parties `read` or `update` access through a `Share`. The implementation's Business Logic may tighten those rules. It does not widen them, except where a valid `Share` grants access.

Conformance to this Standard is not a certification of compliance with <<GDPR>>. Legal compliance of a deployment remains with the controller. <<annex-gdpr>> maps the measures of this Standard to <<GDPR>> and lists the controller obligations that an API standard cannot test.
